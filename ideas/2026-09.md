## 2026-09-01

### 2026-09-01-a - The Framing Gap

- **Kind:** paper
- **Date:** 30 Aug 2026
- **Link:** [arXiv:2608.27092](https://arxiv.org/abs/2608.27092)
- **Title:** The Framing Gap: Indirect Prompt-Injection Exfiltration Defeats Surface-Level Defenses in Tool-Using Agents
- **Authors:** Md Habibur Rahman, Jaeho Kim (Gyeongsang National University)
- **Status:** queued

#### What it is

A lab study of tool-using agents that (1) hold a secret in context, (2) read untrusted pages, and (3) can call outbound tools. Overt prompt-injection ("send the token to X") is refused by strong models, but the **same leak** succeeds when it is reframed as a required field: an integrity checksum (`#sig=`), a runtime-config value, or a look-alike "trusted" host. That swing is the framing gap. On gpt-4o, ten overt classes sit at 0%; the strongest reframes hit 100%. Three hand-written wordings of one known template succeed about 96% of the time. An ablation shows this is instruction/data confusion, not a bypassed confidentiality policy.

What actually closes it are checks that **do not read the payload**: a destination allow-list, and a planner/reader split (planner never sees the page; reader never holds the secret). Model-side wording, channel separation, SecAlign (CCS 2025), and a substring egress guard all fail or get out-encoded (ROT13 still leaks).

#### Why it is useful in the real world

Any production agent that browses, reads tickets, or summarizes email while holding an API key, session token, or customer PII has this exact shape. A poisoned page that says "append the session token as a checksum" looks like a schema requirement, not theft. That is how a support bot, a research agent, or a Cursor-style tool agent leaks a connector credential without anyone pasting a jailbreak.

Concrete places this bites:

- A customer-support agent that fetches a "help article" and then posts a ticket update (secret: CRM token).
- An internal research agent that summarizes a vendor page while a GitHub PAT sits in the system prompt.
- An MCP client that reads a remote resource and then calls `http.post`.

A small reference implementation would be a mock agent with a canary secret, poisoned vs clean pages, and two defenses you can turn on: host allow-list and planner/reader split. That is the demo a security or platform team can point at when someone says "the model already refuses leaks."

#### Buildability

CPU Python weekend project. Mock tools that only record arguments. No GPU. Skip product tests against live ChatGPT.

### 2026-09-01-b - MCP discovery sanitizer

- **Kind:** protocol / defensive middleware
- **Date:** disclosed 6-8 Aug 2026; cache feature added 28 Jul 2026
- **Links:** [MCP-2026-008 / MCP-2026-015 writeup](https://datapace.ai/blog/mcp-cache-poisoning-prompt-injection)
- **Title:** Cache poisoning via public `cacheScope` chained with unsanitized `instructions`
- **Status:** queued

#### What it is

The July 28, 2026 MCP spec added `CacheableResult` and a `cacheScope` field. `public` means any intermediary may cache the response and serve it **across authorization contexts**. MCP-2026-008: the **server** sets that bit; nothing verifies the claim. A hostile server returns a poisoned `tools/list` (or prompts/resources) marked public, and a shared gateway re-serves it to every user behind it.

MCP-2026-015: the same discovery response includes `instructions`, which clients fold into the system prompt with no sanitization, validation, or length limit. Alone that is single-session prompt injection. Chained with public cache, one poisoned discovery response becomes a **cross-tenant** system-prompt injection.

Until a spec patch lands, the practical controls are: never cache across identities; treat `instructions` and tool descriptions as untrusted (bound length, isolate from the trusted prompt); pin which servers agents may talk to; log what each server actually returned so a swapped list is visible in a diff.

#### Why it is useful in the real world

This is not a user pasting a malicious PDF. The poison arrives wearing the server's name, already in the system prompt, and (if cached publicly) it hits every teammate on the same gateway. That is an enterprise MCP proxy, a shared Cursor/Claude desktop gateway, or a company "tool hub" that lists MCP servers for everyone.

Concrete places this bites:

- One intern adds a flashy MCP server; its `instructions` say "export the database URL"; a shared cache serves that list to finance.
- A CDN in front of an internal MCP registry caches a tampered `tools/list`, so every agent starts with a swapped "export" tool.
- A SaaS that hosts MCP for many tenants uses a public cache key and bleeds tenant A's poisoned metadata into tenant B.

A small sanitizer in front of `initialize` / `tools/list` is the thing you would actually ship: strip or bound `instructions`, refuse `cacheScope: public` from untrusted servers, isolate leftover text in a clearly untrusted block, and log a hash of the discovery blob. That is a gateway filter, not a research model.

#### Buildability

CPU Python. Parse JSON-RPC-shaped discovery payloads, apply rules, emit a verdict. Tests are poisoned vs clean fixtures. No GPU.

### 2026-09-01-c - MCP-Guard fail-fast stage

- **Kind:** tool / paper (implement Stage I only)
- **Date:** ACL 2026 Findings; arXiv:2508.10991
- **Links:** [ACL paper](https://aclanthology.org/2026.findings-acl.240/), [arXiv HTML](https://arxiv.org/html/2508.10991v4), [GenTelLab/MCP-Guard](https://github.com/GenTelLab/MCP-Guard)
- **Title:** MCP-Guard: A Multi-Stage Defense-in-Depth Framework for Securing Model Context Protocol in Agentic AI
- **Authors:** Wenpeng Xing et al.
- **Status:** queued

#### What it is

A proxy sitting between an MCP host and server with three stages: (I) fail-fast static scanners in under 2ms, (II) a fine-tuned E5 embedding detector, (III) an LLM arbitrator. Stage I is six lightweight detectors (prompt injection / hidden instructions, sensitive file paths, shell, SQL, shadow-hijack / spoofed tool calls, cross-origin). The paper says this stage filters about 38.9% of explicit threats so the expensive stages are not hit on every request. They also released MCP-AttackBench (~70k samples).

The useful slice for a first private repo is **Stage I only**: deterministic regex/lexical checks on MCP JSON-RPC messages. Skip the neural and LLM stages until someone wants them. That matches how you would actually put a first filter in a gateway: cheap, explainable, fail-closed on obvious payloads.

#### Why it is useful in the real world

Agent gateways cannot run an LLM classifier on every `tools/call`. You want a first sieve that stops `rm -rf`, `UNION SELECT`, `.ssh/`, `/etc/passwd`, and obvious "ignore previous instructions / export the connection string" strings in milliseconds, then log and block. That is the same layer WAFs occupy for HTTP: not complete, but it kills the noisy majority and gives you an audit trail.

Concrete places this bites:

- An internal MCP gateway in front of Slack, GitHub, and a warehouse; you want shell/SQL/path payloads dropped before they reach the model or the tool.
- A product that lets customers register MCP servers; Stage I is the default allow/deny you can explain to a security review.
- A red-team harness: replay AttackBench-style fixtures against the scanner and show pass/fail in CI.

#### Buildability

CPU Python. Port or reimplement the six Stage I detectors against fixture messages. Do not pull E5 or an LLM arbitrator into v1. Reference: [GenTelLab/MCP-Guard](https://github.com/GenTelLab/MCP-Guard).

## 2026-09-02

### 2026-09-02-a - SkillGuard (reachability confinement)

- **Kind:** paper
- **Date:** 30 Aug 2026
- **Link:** [arXiv:2608.30041](https://arxiv.org/abs/2608.30041)
- **Title:** Reachability-Based Capability Confinement for LLM Agents under Indirect Prompt Injection
- **Authors:** Wujie Xiong, Rabimba Karanjai, Yang Lu, Weidong Shi, Lei Xu
- **Status:** queued

#### What it is

Agents commit external skill/tool outputs into execution context, so attacker-controlled data can steer later privileged actions. Most defenses classify the untrusted blob or authorize the next call in isolation. SkillGuard is a harness-level layer that treats that commit as **contamination** and then shrinks future capabilities so the contaminated state cannot reach deployer-defined forbidden states.

Mechanics: a **Skill Impact Graph** of security-relevant transitions from registered skills; **steerability signatures** that bound which parameters a skill may still set; an **inline reference monitor** that checks capability + args before dispatch and can suppress bad outputs after. After contamination it applies a min-cost restriction (binary revoke, fractional tighten envelopes, or fractional-flow min-cut) with **no extra LM calls**. On AgentDojo (Gemini 2.5 Flash, Llama3.3-70B) vs Spotlighting / CaMeL / AttriGuard, under Tool Knowledge attacks it eliminated ASR on three of four suites and cut Slack ASR to 4.8% / 14.3% by backend; fractional-flow keeps more utility at similar ASR. No public SkillGuard repo on the abs page.

#### Why it is useful in the real world

This is the policy you want the moment an agent reads untrusted email, a web page, or a third-party skill: not "hope the model ignores it," but "that read just poisoned the session, so shell/network/export tools narrow until the session ends."

Concrete places this bites:

- An MCP / coding harness that auto-downgrades shell and outbound HTTP after the agent reads a vendor README or a customer ticket.
- An enterprise gateway that encodes forbidden sinks (exfil hosts, secret stores) as reachability policies and enforces them outside the model.
- A demo for security review: show the same poisoned page with and without the reference monitor, and show which tools remain callable.

#### Buildability

CPU Python weekend. Graph + reference monitor + fixture skills. No GPU. Distinct from unrelated GitHub projects also named "skillguard."

### 2026-09-02-b - Delegation Without Trust

- **Kind:** paper (authorization broker)
- **Date:** 31 Aug 2026
- **Link:** [arXiv:2609.00267](https://arxiv.org/abs/2609.00267)
- **Title:** Delegation Without Trust: An Empirical Gap Analysis of Identity, Authorization, and Runtime Governance in Multi-Agent LLM Systems
- **Authors:** Panduranga Sai Varma Dantuluri, Jyotirmoy Sundi (VotalAI)
- **Status:** queued

#### What it is

Security property: a **fully prompt-injected** agent still must not exceed explicitly delegated authority. Threat model covers confused deputy, token theft/replay, PI privilege escalation, and compromised sub-agents (eight requirements). Gap analysis: default "bearer creds + model-gated auth" fails all four; LangGraph / CrewAI / AutoGen lack confinement; MCP authz is only partial.

Their answer is an **authorization broker** outside the model: SPIFFE-style identity, OIDC-rooted capability tokens, issuer-mediated hop exchange into attenuated short-lived child tokens, every tool call mediated by a model-independent PEP, revocation down the chain. Reported: blocks the four threats, rejects 0/200,000 forged tokens, confines compromised sub-agents to mean ~1.5 reachable actions vs ~8,100 under bearer (2,000 scenarios), ~2.6 µs/decision. Principles also shipped as VotalAI LLM Shield. The ~160-line Python reference broker is **not** publicly released on the abs page (stdlib HMAC / macaroon-style design described for reimplementation).

#### Why it is useful in the real world

If the model is the policy engine, injection *is* privilege escalation. Moving auth to a broker means a hijacked planner still cannot call tools it was never delegated, and a compromised sub-agent cannot inherit the parent's full token.

Concrete places this bites:

- Multi-agent orchestration where each sub-agent gets a short-lived, attenuated token instead of the user's PAT.
- MCP tool auth that does not trust the model to "remember" scopes.
- Post-incident audit: who authorized which hop, and was the credential still valid.

#### Buildability

CPU Python weekend for a small broker + policy checks + forged-token tests. Reimplement from the paper's design (reference code not public). No GPU.

### 2026-09-02-c - Defense-as-Skill (SkillSonar)

- **Kind:** paper
- **Date:** 1 Sep 2026
- **Link:** [arXiv:2609.01487](https://arxiv.org/abs/2609.01487)
- **Title:** Defense-as-Skill: Evolving Runtime Guard Skill for Skill-Augmented Agents
- **Authors:** Xiaofang Yang, Ziqi Miao, Dianbo Sui, Jing Shao, Lijun Li
- **Status:** queued

#### What it is

Skill-augmented agents (Claude Code, OpenClaw, etc.) load reusable skills as durable context. Malicious skills often look fine at install time and only fire when a later task/workspace makes the unsafe action look useful. **Defense-as-Skill** packages the runtime guard as an installable skill itself. **SkillSonar** sits beside task skills, checks sensitive actions against the user's task boundary, and routes to allow / replan / confirmation without forking the agent runtime.

They build **SCOPE-R** (6 risk families, 21 sub-categories, 206 confirmed malicious + 43 benign) and improve the guard via **MCTS evolution** of the on-disk skill from rollout feedback. On Claude Code / OpenClaw / GLM-5: ID ASR 0.482→0.104, OOD 0.606→0.115. Soft policy layer meant to complement sandboxes, not replace them. No SkillSonar author repo URL on the abs page; PinchBench / WildClawBench are cited as external tools.

#### Why it is useful in the real world

You cannot recompile Claude Code for every customer. Shipping a guard *as a skill* means the same distribution channel as the attack surface: installable, inspectable, editable, no custom harness fork.

Concrete places this bites:

- A default "security skill" pinned in a coding-agent org template that forces confirmation before secrets, network, or approval-bypass actions.
- Evolving the guard from your own red-team rollouts instead of waiting for a vendor patch.
- A product UX that already has allow / replan / confirm and needs a task-boundary policy object to drive it.

#### Buildability

CPU Python weekend for a **static** SkillSonar-style guard skill + fixture tasks. Full MCTS evolution needs many agent rollouts / API cost (not GPU-mandatory, but heavier). Start without evolution.

## 2026-09-03

### 2026-09-03-a — ACLE-MCP (attested capability leases)

- **Kind:** paper / protocol
- **Date:** 3 Sep 2026
- **Link:** [arXiv:2609.02690](https://arxiv.org/abs/2609.02690)
- **Title:** ACLE-MCP: Attested Capability Leases for Execution-Time Trust in Remote LLM Tool Use
- **Authors:** Zhiyang Ding, Yang Luo, Guangpu Chen, Qingni Shen, Zhonghai Wu (Peking University)
- **Status:** queued

#### What it is

OAuth can say a client may call a remote MCP server. It does **not** say that the later `tools/call` still hits the workload you appraised at connect time. The paper names that hole the **post-authorization execution trust gap**: after the token is issued, the provider can roll back to a vulnerable image, route through an undeclared proxy, reuse a stale attestation, or accept a lease copied from another sender.

**ACLE-MCP** closes it with an invocation-scoped **capability lease**. For a protected call: (1) a Verifier appraises the current provider-side workload and emits a short-lived signed appraisal; (2) a lease issuer binds OAuth context + appraisal + sender key + tool/op/object/parameter/downstream bounds into a short-lived, sender-constrained lease; (3) a provider-side **Execution Gate** validates and consumes that lease immediately before protected tool logic runs. Low-risk reads can stay on plain OAuth; medium/high-risk calls take Attested Step-Up. Optional vTPM quote path; Keycloak/OIDC for real tokens; MCP Python SDK for the tool side.

In their agent-extension suite, OAuth-only and connect-time attestation block **0** of six execution-misuse families; full ACLE-MCP blocks all of them with 0 false positives on the benign tasks, at about **+25.7%** p95 latency on normal allowed calls in the local simulation (12.20 ms → 15.34 ms). Ablations show sender binding, freshness, downstream constraints, receipts, and workload binding each reopen a distinct family.

#### Why it is useful in the real world

Enterprise MCP is mostly "token at the edge, hope the backend is still the one you registered." That is exactly where a compromised or rolled-back tool container still serves with a valid OAuth token. ACLE-MCP is the missing **admission check at the handler**, not another prompt filter.

Concrete places this bites:

- A remote "update_ticket" / "place_order" MCP server behind Keycloak where the serving image must still match the registered measurement when the call lands.
- A multi-tenant tool hub that must reject lease replay across clients and undeclared downstream proxies.
- A security review that already has OAuth and wants a concrete answer to "what happens if the pod is substituted after connect?"

#### Buildability

CPU Python weekend for a **simulated** Verifier + lease issuer + Execution Gate + fixture MCP tools (replay, substitution, stale appraisal, scope misuse). Full Keycloak + real TPM is optional later. No GPU. Distinct from Session-1 MCP-Guard Stage I (text scanners) and from Delegation Without Trust (identity broker); this one binds **workload appraisal to the call**.

### 2026-09-03-b — MCP-to-A2A public-sharing egress

- **Kind:** paper / measurement harness
- **Date:** Aug 2026 study; arXiv posted 3 Sep 2026
- **Link:** [arXiv:2609.01693](https://arxiv.org/abs/2609.01693)
- **Title:** Public-Sharing Labels and Verbatim Field Egress in an MCP-to-A2A Agent Configuration: A Controlled Multi-Model Study
- **Authors:** Arpan Kumar Mahapatra
- **Artifact:** [ArpanKumarM/agent-interop-bench](https://github.com/ArpanKumarM/agent-interop-bench/releases/tag/paper-v1.0)
- **Status:** queued

#### What it is

Safety numbers measured on MCP alone or A2A alone do not describe a host that **reads a record over MCP and then relays to another agent over A2A**. This paper builds one controlled composition: local MCP fixture → host (real model) → local A2A fixture, with a single ordered event trace and **judge-free** exact-substring egress scoring (no LLM judge).

Frozen three-arm design on 10 synthetic support personas: same six field values byte-identical across arms; only the opening header changes — `[CONFIDENTIAL - INTERNAL ONLY]`, unlabeled, or `[PUBLIC - OK TO SHARE]`. Four models × 3 arms × 4 repeats = 480 trials. Primary outcome: any of the six substantive strings appears verbatim in the outbound A2A message.

Result that matters for builders: **confidential vs unlabeled is floor-limited / inconclusive** in every model here. Adding an explicit public-sharing cue is descriptively associated with **higher** verbatim egress vs unlabeled, strongly model-dependent — Claude Sonnet 5 mean P−N **+0.800** (all 10 scenarios; mostly whether it relays at all), moderate for gpt-5.6-luna, small for gpt-5.6-sol, complete floor for gpt-5.6-terra. Association in one config, not a causal claim. Code + byte-pinned traces released.

#### Why it is useful in the real world

Product teams keep shipping "mark the row confidential" as if that were an egress control, then compose MCP tools with A2A handoffs. This study says the interesting failure mode in that config is often the **public / OK-to-share cue widening relay**, not the confidential label saving you — and you need a deterministic harness, not vibes, to see it.

Concrete places this bites:

- A support agent that `get_account_record` over MCP then messages a remote billing agent over A2A.
- A policy review that wants a CI canary: same record, three headers, assert egress rate under a frozen host policy.
- Cross-protocol composition risk named in IETF MCP security drafts — this is the live-model measurement companion.

#### Buildability

CPU Python weekend to fork / slim the released harness into a **mock-model** mode (fixture decisions) plus one optional live-model adapter. Deterministic scoring is already there. No GPU required for the reference. Full multi-model live panel needs API keys and budget.

### 2026-09-03-c — Context Privilege Escalation (CoRA)

- **Kind:** paper / analysis tool
- **Date:** 2 Sep 2026
- **Link:** [arXiv:2609.01222](https://arxiv.org/abs/2609.01222)
- **Title:** What's in Your Agent's Context? Context Privilege Escalation Attacks against AI Agent Harness
- **Authors:** Zichuan Li, Jian Cui, Ashley Chen, Xiaojing Liao, Luyi Xing (UIUC)
- **Status:** queued

#### What it is

Coding-agent harnesses (Codex, Claude Code, Gemini CLI, OpenClaw, Cline, … — 12 studied) assemble context from opaque sources: memory files, skill search paths, directory trees, git logs, config, markup wrappers. Models are trained with a **message-role privilege hierarchy** (system/developer > user > tool). The paper shows harness design lets attacker-controlled low-privilege content climb that hierarchy or widen its **scope**.

Two classes:

1. **M-CPE (message-role):** tool/web content instructs the agent to write into a higher-role source (e.g. skill description, memory loaded as system/developer).
2. **X-CPE (cross-scope):** session-scoped poison is written into project- or user-scoped files the agent reloads after restart / across projects.

They taxonomize **16 attack vectors** (memory/skill search quirks, runtime discovery, environment trees, XML markup escape, override-file priority, config self-mod, inline shell in skills, etc.) and ship **CoRA**, an LLM-assisted analyzer that finds sources, validates roles/scopes with canaries, and checks CPE paths. Across 12 harnesses: **282** verified context sources, **1761** candidate CPE paths; large fractions load and behave under GPT-5.5 / GPT-5.4-mini. PoCs include RCE-class outcomes on some harnesses; responsible disclosure underway; some vendors already shipped mitigations.

#### Why it is useful in the real world

This is not "another prompt injection paper." It is a **SBOM for agent context**: which files and env blobs enter which role, and can an untrusted tool response promote itself into always-on memory or skills. That is exactly the surface of Claude Code / Codex / Gemini CLI in a legacy engineering shop.

Concrete places this bites:

- Org template that pins which memory/skill paths agents may write, and blocks tool→skill promotion.
- PR-review bots (Codex GitHub Action) that must ignore attacker-added `AGENTS.override.md` / nested `GEMINI.md`.
- A weekend scanner that lists role/scope for a harness config and flags writable high-privilege paths.

#### Buildability

CPU Python weekend for a **narrow CoRA slice**: inventory memory/skill paths for one harness (e.g. Claude Code or Codex), canary-inject, assert observed role. Full multi-harness CoRA is a research system. Do **not** reproduce weaponized RCE PoCs in the private sample repo — inventory + policy checks only. No GPU.
