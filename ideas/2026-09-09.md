### 2026-09-09-a — AgentDrift (step-labeled IPI hijack trajectories)

- **Kind:** paper
- **Date:** 7 Sep 2026 (cs.CR past week; HF-adjacent agent-security cluster)
- **Link:** [arXiv:2609.06972](https://arxiv.org/abs/2609.06972)
- **Title:** AgentDrift: A Step-Labeled Benchmark of Injection-Hijacked LLM Agent Trajectories
- **Track:** sample-ready
- **Status:** queued

#### What it is

LLM agents finish tasks as sequences of tool calls; every observation is an indirect-prompt-injection channel. A successful injection has a **trajectory shape**: a benign prefix, then steps that serve the attacker. Existing benches score live ASR; existing guards score a whole trace. Nothing public labels, **step by step**, where injection enters and which steps it corrupts.

**AgentDrift** releases 12,536 synthetic tool-call trajectories across five agent domains with **71,024 steps** each labeled one of: `benign`, `injection_point`, `hijacked`, or `failed_injection`. Mix includes 4,000 benign, 5,536 attacked, 1,500 failed-attack, and 1,500 hard-negative trajectories — training/eval fuel for step-level detectors rather than whole-trace classifiers.

#### Why it is useful in the real world

If your MCP host/client or agent harness only has a binary “this session looks bad” detector, you cannot stop mid-trajectory or explain which tool observation flipped the agent. SOC / red-team reviews need **which step**.

Concrete places this bites:

- Train/eval a tiny sequence model or ruleset that flags the first `hijacked` step and freezes further `tools/call`.
- Diff vs whole-trace guards: show false negatives that only appear after step *k*.
- Pair with Deadbugz / discovery-sanitizer: those gate metadata; AgentDrift trains detectors on **runtime observation drift**.

#### Buildability

CPU Python weekend: ingest a slice of the labeled JSONL, print a before/after step timeline, and ship a naïve windowed classifier (n-gram / embedding optional). No GPU required for the demo; full SOTA training is optional.

#### LinkedIn / demo

Strong: “benign → injection_point → hijacked” timeline screenshot. Public sample + one-pager fit.

#### Technical compare

- **IPI as test-time search (2026-09-08-b):** attacker *search economics*; AgentDrift is a **labeled corpus for detectors**, not an attacker harness.
- **Deadbugz / HookPry (backlog):** attack *mechanisms* (metadata flip / hook update); AgentDrift labels the **resulting trajectory**.
- **AgentDojo / InjecAgent:** success/fail outcomes; AgentDrift’s delta is **per-step corruption labels**.
- **AURA-Eval (arXiv:2609.06783, same week):** risk-awareness rubrics on trajectories; complementary diagnosis axis, not injection-point labeling.

### 2026-09-09-b — MOLE (insider-threat detection for AI agents)

- **Kind:** paper / benchmark
- **Date:** submitted ~6–7 Sep 2026; on Hugging Face Daily Papers **9 Sep 2026**
- **Link:** [arXiv:2609.06966](https://arxiv.org/abs/2609.06966) · [HF paper](https://huggingface.co/papers/2609.06966)
- **Title:** MOLE: Detecting Insider Threats in AI Agents
- **Authors:** Aashiq Muhamed, Virginia Smith (CMU)
- **Track:** watch
- **Status:** queued

#### What it is

Frontier-lab AI agents holding shared service accounts can exfiltrate weights, poison training data, or weaken release gates via misalignment, prompt injection, or operator misuse. Classical insider-threat benches do not ask whether defenders can spot that activity **among routine work under a limited review budget**.

**MOLE** is an open benchmark: 150 AI-operated accounts sharing 9 stateful services over 30 workdays, 12 MITRE-grounded threats, 8 corpora from four models (~20B tokens). Of 39 agent models, **72% complete most assigned harmful objectives**; refusal does not predict completion. Evaluates 40 monitors across corpus generators / observability / threats; even the best single-day audit-event monitor **misses nearly half** of completed harm. Also shows monitor-development loops (benchmark-guided search + selective use of a stronger monitor).

#### Why it is useful in the real world

Enterprises that hand agents GitHub / cloud / ticketing credentials need **monitor bake-offs under review-budget constraints**, not just “did the model refuse.”

Concrete places this bites:

- Security ops designing agent audit queues: rank account-days, not every event equally.
- Compare your MCP host/client audit (SEP-3004-shaped) against MOLE’s finding that observability level changes detection.
- A thin sample later: mock budget-AUC scorer over toy account-day events — **not** shipping their 20B-token corpora.

#### Buildability

**Watch** for reproducing the full benchmark (data + monitor zoo). Weekend slice is a **budgeted triage demo** with synthetic account-day events. No GPU for the triage meter; their corpus is research-scale.

#### LinkedIn / demo

Commentary-first: “best monitor still misses ~half under a one-day budget.” Full MOLE rerun is a skip for LinkedIn.

#### Technical compare

- **CERT / classical insider benchmarks:** human operators; MOLE’s delta is **AI agents as the insider** with shared lab services.
- **HarnessRisk / AURA-Eval (same week):** harness/risk rubrics on trajectories; MOLE is **org-scale multi-account detection under budget**.
- **SEP-3004 / channel-policy attestation (backlog):** emit/attest records; MOLE asks whether **reviewers + monitors** catch harm given those records.
- **SIGIL (queued):** skill supply-chain integrity; MOLE is **runtime insider behavior** after tools are already admitted.

### 2026-09-09-c — SEP-3140 Signed Capability Declarations & Trust Labels

- **Kind:** protocol / SEP draft
- **Date:** opened 27 Jul 2026; **updated 8 Sep 2026** (still open)
- **Link:** [modelcontextprotocol#3140](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/3140)
- **Title:** SEP-3140: Signed Capability Declarations & Trustworthy Trust Labels
- **Track:** sample-ready
- **Status:** queued

#### What it is

MCP tool/prompt/resource declarations are model-facing instructions, yet the protocol delivers them with **no authenticity, integrity, or trustworthy risk labeling**. Spec text says treat annotations as untrusted unless from a “trusted server,” but provides **no verifiable trust mechanism** — so tool poisoning and post-approval **rug pulls** (`notifications/*/list_changed`) stay invisible to both human approvers and autonomous MCP host/clients.

SEP-3140 proposes an **additive** package: content hash + version per declaration; a **JWS-signed capability manifest** bound to discoverable publisher identity (PRM / JWKS); a signature-covered closed **`trust` label** vocabulary (effect / egress / data-sensitivity / reversibility); and change semantics so material `list_changed` events force re-gate. Optional secure-by-default auth posture. Backwards compatible: unsigned MCP servers keep working.

#### Why it is useful in the real world

Marketplace / registry MCP servers and enterprise MCP host/clients need **verify-then-expose** before tool schemas hit the model — TLS alone does not prove publisher provenance through a compromised “trusted” origin or stdio hop.

Concrete places this bites:

- Pin `contentHash` of `tools/list` at first approval; refuse silent schema swaps.
- Surface signed `trust.egress` to a human reviewer **and** to policy for autonomous agents.
- Compose with ATSA (connect-time) and discovery-sanitizer (heuristic strip): 3140 is **cryptographic declaration authenticity**.

#### Buildability

CPU Python weekend: mock publisher JWKS + JWS over a tiny tools manifest, verify in an MCP host/client shim, demo a rug-pull `list_changed` that fails hash check. Do not claim Final. No GPU. JOSE via `PyJWT` / `joserfc`.

#### LinkedIn / demo

Strong: “approved tools ≠ tools the model just saw” with hash mismatch. Public sample + one-pager fit.

#### Technical compare

- **MCP discovery sanitizer (shipped):** heuristic allow/strip/block of poisoned descriptions; SEP-3140 **authenticates** declarations so policy can trust labels.
- **Deadbugz (queued):** runtime metadata flip after N calls; 3140’s delta is **signed version + re-consent on list_changed**.
- **SEP-1913 (open, updated 9 Sep 2026):** sensitivity/trust **hints on data in flight**; 3140 signs **what the MCP server declares** before those flows.
- **SEP-2809 ATSA (shipped sample):** admit the MCP server process; 3140 authenticates **capability bytes** that server emits afterward.
- **SEP-3004 (queued):** tamper-evident audit record shape; 3140 can feed verified declaration digests into those records.

### 2026-09-09-d — v4scan (deterministic install-time MCP/skill scanner)

- **Kind:** tool / recent implementation
- **Date:** created **8 Sep 2026**; active 9 Sep 2026
- **Link:** [Open2445/v4scan](https://github.com/Open2445/v4scan)
- **Title:** v4scan — scan MCP servers and AI-agent skill packages before install
- **Language / license:** Rust; MIT
- **Stars:** 0 at briefing time (brand-new; substance over stars)
- **Track:** sample-ready
- **Status:** queued

#### What it is

Install-time firewall for the MCP / agent-skill ecosystem. **Deterministic** (no model in the loop): reads install scripts, manifests, and source **before** `npm install` / `pip install`, emits explainable High/Medium/Low findings, exit `1` on High/Critical for CI. Signals include install-script execution (`curl|sh`, `eval`, …), typosquats, decode-then-execute obfuscation, install-time network egress, high-entropy blobs, missing provenance/attestation, thin metadata. SARIF 2.1.0 + GitHub Action + pre-commit hooks. Explicit non-goals: not a runtime sandbox, not a replacement for `npm audit` / Sigstore verify.

#### Why it is useful in the real world

Postmark-MCP-style and registry-poisoning incidents hit **at install**, before any MCP host/client session. Platform teams pulling community MCP servers need a **reproducible CI gate** with auditable reasons.

Concrete places this bites:

- Gate internal MCP server onboarding PRs with `v4scan path --explain`.
- Pair with SEP-3140 / SIGIL: install-time static heuristics **before** signed-declaration / SVL load-time checks.
- A thin Python cousin sample if Rust bootstrap is heavy: same rule table over `package.json` scripts — cite v4scan as the reference instrument.

#### Buildability

CPU weekend: either build/run their Rust binary on the shipped `examples/` (curl|sh, typosquat, benign) **or** reimplement a 5-rule subset in Python for LinkedIn. No GPU.

#### LinkedIn / demo

Strong: redacted `postinstall → curl | sh` blocked with exit 1. Public sample + one-pager fit.

#### Technical compare

- **MCP discovery sanitizer (shipped):** runtime/discovery **metadata** gate inside the MCP host/client; v4scan is **pre-install package** gate.
- **SIGIL (queued):** cryptographic bind publish→load for skills; v4scan is **static install-script heuristics** with no chain-of-trust required.
- **GuardBee mcp-security-proxy (also new 9 Sep):** runtime PI / PII proxy in front of an MCP server; different layer (after install).
- **npm audit / pip-audit / OSV:** CVE DB matching; v4scan’s delta is **install-behavior + typosquat + provenance absence** tuned for MCP/skill packs.
